# 调研：跨端如何判定「同一个链接」——身份识别机制

> 版本：**v1.1**（承接 `调研-标签实体纳入事件日志同步-v1.0.md`，同一批调研的第二题）
> 日期：2026-10-25
> 范围：客户端 `reading-share-android`（`db/`、`eventlog/`、`links/`、`ui/`）+ 服务端 `event-log-sync-protocol/app.py` + 协议 `PROTOCOL.md`

## 0. 一句话结论

**跨设备没有真正的身份。当前两端能对上，靠的是 URL（+title）这个自然键，且只在 create 分支生效。**
`links._id` / `entity_id` 是「发起方设备的本地自增号」，跨设备编号空间必然重叠，**不能当身份用**。

## 1. links 表没有自然键

`db/LinkDbHelper.java:93-105` 完整建表 SQL：

```java
 93|    private static final String SQL_CREATE_LINKS =
 94|            "CREATE TABLE " + TABLE_LINKS + " (" +
 95|                    COLUMN_ID + " INTEGER PRIMARY KEY AUTOINCREMENT, " +
 96|                    COLUMN_TITLE + " TEXT, " +
 97|                    COLUMN_URL + " TEXT, " +
 98|                    COLUMN_REMARK + " TEXT, " +
 99|                    COLUMN_SOURCE_APP + " TEXT, " +
100|                    COLUMN_ORIGINAL_INTENT + " TEXT, " +
101|                    COLUMN_TARGET_ACTIVITY + " TEXT, " +
102|                    COLUMN_TIMESTAMP + " INTEGER, " +
103|                    COLUMN_SUMMARY + " TEXT, " +
104|                    "is_pinned INTEGER DEFAULT 0, " +
105|                    "click_count INTEGER DEFAULT 0)";
```

| 列 | 定义 | 约束 |
|---|---|---|
| `_id` | INTEGER PRIMARY KEY AUTOINCREMENT | 本地自增，**唯一身份来源** |
| `url` | TEXT | **无 UNIQUE、无 NOT NULL、无 COLLATE** |
| `title` / `remark` / `source_app` / `original_intent` / `target_activity` / `timestamp` / `summary` | TEXT / INTEGER | 无约束 |
| `is_pinned` / `click_count` | INTEGER DEFAULT 0 | 无约束 |

补充事实：
- 全工程 grep `COLLATE|NOCASE` **零命中** → SQLite 默认 BINARY 排序，`url = ?` 是**大小写敏感 + 空白敏感 + 完全相等**。
- links 表索引只有 `idx_links_title`、`idx_links_timestamp`（`LinkDbHelper.java:273-274`）→ **没有 url 索引**，所有按 url 的查重都是全表扫描。
- `PRAGMA foreign_keys = OFF`（`LinkDbHelper.java:225`）→ 外键不校验。
- 对比：`tags.name TEXT UNIQUE`（`:117`）、`documents.file_path TEXT NOT NULL UNIQUE`（`:154`）—— **links 是唯一一张没有自然键的业务表**。

### `getLinkTitleByUrl` 的准确语义（`LinkDao.java:154-172`）


## 3. identity 的三层

### 第 1 层 · 事件流内的身份 = `(topic, entity_id)`

`eventlog/SqliteEventLogStore.java:242-254`：

```java
243|        Cursor c = db.rawQuery(
244|                "SELECT " + COL_DATA + " FROM " + TABLE_EVENTS +
245|                        " WHERE " + COL_TOPIC + " = ? AND " + COL_ENTITY_ID + " = ?" +
246|                        " AND " + COL_DATA + " IS NOT NULL" +
247|                        " ORDER BY " + COL_PROCESS_TIME + " DESC LIMIT 1",
248|                new String[]{topic, entityId});
```

→ 靠 `(topic, entity_id)` 找「上一条同实体事件」，其 payload 填进新事件的 `old`（`eventlog/EventLogClient.java:432-434`）。

事件表 `eventlog/EventLogSchema.java:63-74`，`entity_id TEXT NOT NULL`（`:69`），索引 `idx_events_entity ON events(topic, entity_id)`（`:79-82`）→ **同 topic 下 entity_id 即实体身份**，协议 §5.4 折叠以 entity_id 为 map key（`PROTOCOL.md:424-448`）。

### 第 2 层 · 折叠时，服务端 entity_id 直接当本地主键

- `links/LinkEventApplier.java:84-100` `decode()`：`Long.parseLong(entityId)` → `item.setId(serverEntityId)`（`:91-94`）—— **覆盖 payload 里的本地 id**。
- `db/LinkDao.java:100-123` `replaceById()`：把 `item.getId()` 写进 `_id` 列（`:103`），`insertWithOnConflict(..., CONFLICT_REPLACE)`（`:119-121`），再 `updateLinkTags(item)`（`:122`）。

→ **本地 `links._id` 被服务端 entity_id 顶替**，本地自增身份在此步失效。

### 第 3 层 · 跨设备的自然身份 = URL（+title），只在 create 分支生效

见 §2、§4。

## 4. 两个实锤隐患（代码路径 + SQLite 实测）

### 隐患 A：entity_id 跨设备必然重叠，重叠即「本地行被顶替」

**完整路径**：
`MainActivity.java:742-746`（本地 `_id` → `String.valueOf(newLink.getId())` 作 entity_id）
→ 服务端原样存（`app.py:200,203`）
→ 另一端取回（`HttpEventLogPuller.java:114`）
→ `EventLogClient.pull` 逐条 `linkApplier.apply(e)`（`eventlog/EventLogClient.java:343-350`）
→ `LinkEventApplier.decode()` 把 entity_id 塞进 `item.setId`（`:89-94`）
→ `LinkDao.replaceById()` 用 `CONFLICT_REPLACE` 写 `_id`（`:103, :119-121`）。

**SQLite 实测一：外来 id 覆盖本地已有行**
```
本地插 3 条：_id=1,2,3
远端 entity_id=2 到达 → INSERT OR REPLACE _id=2
  结果: [(1,'A'), (2,'REMOTE','http://remote'), (3,'C')]   ← 本地第 2 行内容消失
```
`INSERT OR REPLACE` 在 SQLite 里是 **DELETE + INSERT**，目标 `_id` 上的本地行直接被替换。
两台设备各自从 1 开始自增 → **entity_id 重叠是必然命中，不是罕见竞态**。

**SQLite 实测二：AUTOINCREMENT 序列被推高（不会重复发号）**
```
写入显式 _id=500 → sqlite_sequence.seq = 500
下一条本地插入 → _id = 501
```
→ 外来 id **不会**被后续自增重复分配，但会让本机 id 与对端 id **永久错位**，之后每次推送都用「对端视角的 id」当 entity_id，碰撞持续累积。

**SQLite 实测三：标签关联的最终归属（修正一个常见误判）**
```
before: links=[1:LOCAL-2, 2:LOCAL-3], link_tags=[2->1]
REPLACE _id=2 (远端覆盖)  → link_tags 仍是 [2->1]      ← 中间态：孤儿关联还在
updateLinkTags(item) 的 DELETE link_tags WHERE link_id=2 → link_tags = None  ← 最终被清
```
`replaceById` 最后调 `updateLinkTags(item)`（`LinkDao.java:122`），后者先 `DELETE FROM link_tags WHERE link_id = ?`（`:669-673`）再按 payload 重建 → **本地那条链接的标签关联会被远端 payload 的 tags 顶掉，不是「挂到别人链接上」，是「本地标签丢失」**。
（`tags` 表里的孤儿 tag 行不会自动清理，但那是无害残留。）

**远端 delete 事件会误删无关的本地链接**：`LinkEventApplier.java:77-82` → `linkDao.deleteLink(entityId)` → `LinkDao.java:193-198` `DELETE FROM links WHERE _id = ?`。远端设备删掉它自己的第 2 条链接 → 本端**本地第 2 条链接被连带删除**（且它自己那条 create 事件还在事件流里，状态不自洽）。该路径**会**清 `link_tags`（`LinkDao.java:185-189`）。

### 隐患 B：同步去重只在 create 分支，update 分支没有去重

**核实：属实。**
```java
 56|    private void handleCreate(EventRecord event) {
 57|        LinkItem item = decode(event);
 ...
 61|        String existingTitle = linkDao.getLinkTitleByUrl(item.getUrl());
 62|        if (existingTitle != null && existingTitle.equals(item.getTitle())) {
 63|            return;
 64|        }
 ...
 67|        linkDao.replaceById(item);
 68|    }
 69|
 70|    private void handleUpdate(EventRecord event) {
 71|        LinkItem item = decode(event);
 72|        if (item == null) return;
 73|        // update: 服务端版本为权威；CONFLICT_REPLACE 保证本地之前没有也能落地
 74|        linkDao.replaceById(item);
 75|    }
```

**后果**：
1. 对端改标题 → 发一条 update（entity_id = 对端本地 id）→ 本端用它覆盖 `_id` 相同的本地行。id 恰好对上别人的行 → 本地行被顶替 + 本地标签丢失；id 对不上 → 本端多出一条与本地那条 URL 相同、id 不同的重复行。
2. 同一条逻辑链接在本端出现**两份**（一份本端 `_id`，含本地标签/点击数；一份对端 id 覆盖出来的，标签来自 payload）。
3. 后续对两份分别 update/delete → 各自产生不同 entity_id 的事件 → **分叉再也合不回来**。
4. 讽刺点：create 分支那个「URL+title 去重」注释自陈就是为了消解跨设备 id 冲突（`LinkEventApplier.java:59-60`），但 update 分支没跟上 → **补救只覆盖了「新建」这一种事件类型**。

## 5. 会把同一 URL 判成两条不同链接的场景（量化）

| # | 场景 | 后果 |
|---|---|---|
| 1 | 两台设备各自保存同一 URL | 各自自增得到不同 `_id` → 事件流里是两个实体，协议层无法识别为同一条 |
| 2 | 同 URL 不同 title | `handleCreate` 要求 title 也相等 → **不跳过** → 用服务端 id 新插一行 → 本地出现同 URL 两行、id 不同 |
| 3 | URL 归一化差异 | `http://x` vs `https://x`、尾部 `/`、末尾 `?ref=`、host 大小写、`%20` vs `+` → 全部判为不同链接（`model/LinkItem.java:92-104` 的 `extractUrl` 只截到第一个空格，不 trim 不 lowercase） |
| 4 | update 分支无去重 | 同一条链接在两端各有一份，id 不同（§4 隐患 B） |
| 5 | MainActivity 保存路径无查重 | 同一台设备连点两次保存 = 两条独立记录，各自发 create |

## 6. 结论：id 在跨设备场景能不能当身份？

**不能。**

- **id 的本职**：本地自增主键 + 本地行指针（`LinkDao.java:177-207`、`:909` `getLinkById`、`link_tags.link_id`）。**单机语义下**它就是身份，没问题。
- **跨设备时它是什么**：`entity_id` 被定义为「发起方设备的本地自增号」。协议要求「entity_id 同一 topic 内全局唯一」（`PROTOCOL.md:179`），§5.4 折叠拿它当 map key（`PROTOCOL.md:424-448`）—— 但客户端送上的是**设备内局部序号**，从第一秒就违反该约束。
- **服务端不会拦**：纯管道，只 `SELECT ... ORDER BY process_time`（`app.py:332-360`），不折叠不消歧，错误一路透传到两端。
- **因此两端「稳定对上同一个链接」实际依赖 URL（+title）这个自然键** —— 且要求 url 字节级相等 + title 字节级相等、且因 `LIMIT 1` 无序而判定不确定、且**只在 create 一条路径上**、且 `links` 表无 DB 级自然键兜底。

## 7. 修复方向（结论，未实施）

把跨设备身份从「本地自增号」换成**设备无关的自然键**：

| 实体 | 自然键 | 依据 |
|---|---|---|
| 链接 | 规范化后的 URL | 需新增归一化函数（trim / 小写 host / 去尾斜杠 / 统一 http(s)）+ `links.url` 加 UNIQUE 索引 |
| 标签 | `tags.name` | **已经是 `TEXT UNIQUE`**（`LinkDbHelper.java:117`），无需改造 |

配套：本地 `_id` 退回纯本地主键职责，与 event id 解耦；`entity_id` 携带自然键；applier 按自然键定位本地行而非按 `_id`；update 分支补去重；删除事件按自然键删。
