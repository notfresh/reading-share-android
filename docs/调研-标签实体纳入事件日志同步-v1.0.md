# 调研：把「标签」作为实体纳入事件日志同步

> 版本：**1.0**（首版调研，未动代码）
> 日期：2026-10-25
> 范围：客户端 `reading-share-android` + 服务端 `event-log-sync-protocol` + 协议 `PROTOCOL.md`
> 性质：**只读调研**。本文档所有结论均给出 `文件:行号`，可直接回源码逐行核对。
> 需求来源：用户希望「删除一个标签」这个操作也能多端同步，即把标签当成一个可同步实体类型。

## 0. 一句话结论

**服务端 0 改动，全部工作量在客户端。** 实体类型维度就是 `topic`，服务端是纯 append-only 管道、不做折叠，`app.py` 全文 grep `link` 零命中；id 公式已含 `topic`、游标 key 也含 `topic`，新增 `"tags"` topic 天然与服务端已有数据不冲突。

客户端有三处硬闸门必须打开（详见 §3），以及两个语义坑比改代码本身更难（详见 §5）。

### 1.3 幂等 id（eid）公式

**位置：`eventlog/EventLogClient.java:443-458`**

```java
public static String computeId(String topic, String deviceId, String eventTime,
                        String entityId, String action) {
    String raw = topic + "|" + deviceId + "|" + eventTime + "|"
            + entityId + "|" + action;              // :445-446
    ... SHA-256 → 前 8 字节 → 16 位 hex            // :448-454

```

五元组 = **topic（实体类型）+ device_id + event_time + entity_id + action**。
→ **`topic` 已在首位，新增 `"tags"` 的 id 天然与 link 事件不冲突，公式无需改。**

## 3. 客户端三处硬闸门（必须打开才能支持第二个 topic）

### 闸门 1：折叠 applier 按 topic 守卫，且只注册了一个

- `links/LinkEventApplier.java:40-42`：`if (!TOPIC_LINKS.equals(event.getTopic())) return;` —— 非 `links` topic 直接丢弃
- `eventlog/EventLogClient.java:349`：`linkApplier.apply(e)` —— pull 循环里**只调这一个** applier
- `eventlog/EventLogClient.java:29`：字段是单个 `private final LinkApplier linkApplier;`
- 全工程 `implements LinkApplier` 只命中 `LinkEventApplier.java:25`
- 其它 topic 的事件会落到 `EventLogClient.java:140` 的 `NOOP_LINK_APPLIER`，**被静默忽略**

→ 需要：新增 `TagEventApplier`，并把 applier 改成能按 `event.getTopic()` 分派（dispatcher）。

### 闸门 2：push / pull 写死 `"links"`

- `App.java:181-182`：`pushPending("links")` + `pull("links")`（启动同步）
- `EventLogActivity.java:107-108`：手动同步同样写死
- 协议 §10.6 的约定是「每次同步一个 topic；跨 topic 客户端循环」→ 需要按 topic 列表循环调用

### 闸门 3：事件日志 UI 只展示 `links` topic

- `EventLogActivity.java:266`：`count("links")`
- `EventLogActivity.java:284`：`untilByProcessTime("links", useCursor, PAGE_SIZE)`
- → 需按 topic 过滤 / 分组展示，否则 tags 事件拉回来但在 UI 里看不见。

### 不需要改的地方

- **游标 key 已含 topic**：`EventLogClient.java:380-382` push = `push:<baseUrl>:<topic>`，:384-386 pull = `pull:<baseUrl>:<topic>` → 新 topic 自动独立游标，天然满足协议 §10.5 双游标契约。
- **服务端**：`app.py` 无需任何代码修改（见 §4）。

### 5.1 存储：两张独立表，links 表**没有** tags 列

`db/LinkDbHelper.java`：

- `SQL_CREATE_TAGS` :114-117 → `tags(_id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT UNIQUE)`
- `SQL_CREATE_LINK_TAGS` :119-125 → `link_tags(link_id, tag_id, PRIMARY KEY(link_id, tag_id), FOREIGN KEY...)`

### 5.2 坑 1：`entity_id` 对 tag 必须用**标签名**，不能用 `tags._id`

`tags._id` 是本地自增（`LinkDbHelper.java:116` `INTEGER PRIMARY KEY AUTOINCREMENT`），**跨设备不可比**；`tags.name` 是 `TEXT UNIQUE`（:117），跨设备天然稳定。

且 **delete 事件的 data 会被服务端丢弃**（`app.py:203` `data = None if action == "delete"`），标签名只能靠 `entity_id` 携带。
→ `entity_id = tagName`，符合协议「同一 topic 内全局唯一」（`PROTOCOL.md:174`）。

不能照搬 `LinkEventApplier.java:79-81` 的 `parseEntityId` → `Long.parseLong` → `if (entityId <= 0) return;`（:102-109）：tag 无数字 id，这套逻辑会把所有 tag 事件当无效丢弃。**tag 的 applier 要按名字删。**

### 5.3 坑 2：标签可能在对端「复活」

`model/LinkJson.java:29-35` 把 `tags` 数组写进了 link 的 data payload；折叠侧 `links/LinkEventApplier.java:56-75` → `linkDao.replaceById(item)`（:67 / :74）→ `db/LinkDao.java:122` `updateLinkTags(item)` 重建 `link_tags` 行 → 内部调 `getOrCreateTag`（`LinkDao.java:684-703`）。

⇒ **「某链接有哪些标签」这条信息已经通过 `links` topic 同步了**（这部分不用重做）。
⇒ 但 A 端删了标签 `foo`，B 端若收到任一 payload 带 `foo` 的 link 事件，`getOrCreateTag` 会**把 `foo` 重新建出来**。
⇒ 真正要补的只有两件事：
1. **标签实体本身的删除事件**（`tags` topic 的 delete）——对端按名字删 `tags` 行。
2. **级联删掉的那些 link 的 delete 事件**（`links` topic）——否则 B 端留着那些「只有 foo 这一个标签」的链接。

## 8. 待用户拍板的决策点

**标签删除时，要不要连带同步「级联删掉的那些链接」？**

- **要** → 两端数据不会分叉，但改动面变大（要同时为每个被级联删的 link 发一条 `links` delete 事件）。
- **不要** → 只删标签，对端会残留那些「只有这个标签」的链接，两端数据分叉。

> 调研倾向：**要**。否则 `deleteTagWithLinks` 执行完两端数据就不一致了。
